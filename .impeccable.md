## Design Context

### Users

Platform engineers first: people running their own fleet of Cloud Hypervisor
and Firecracker hosts, fluent in VMs, hosts, storage and networking, who use the
`qarax` CLI daily. The web UI is where they check health and act without
recalling flags, most of all during an incident (a host down, a VM stuck
pending, a start that failed). Close behind: developers who use qarax for
sandboxes and AI-agent environments, at home with APIs but less so with
hypervisor vocabulary. Both often have a terminal open beside the UI.

Jobs to be done:
- See what runs where, and whether it is healthy.
- Start, stop, pause, resume or delete a VM, and understand why one won't.
- Get to a VM's console or its log.
- Find out what went wrong and what to do next.

### Brand Personality

Welcoming, sturdy, plain-spoken, in PatternFly's clothes. It explains itself
to a newcomer without slowing down an expert.

Emotional goals: confidence (I understand what is happening), calm during
incidents (no alarm fatigue), and being welcomed rather than tested.

Voice: plain language, sentence case, the same nouns as the API and CLI (VM,
host, storage pool, sandbox) so what people learn here works in `qarax` and
back. Errors say what happened and what to do about it; empty states point to
the next step, with the CLI command when there is no UI for it yet.

### Aesthetic Direction

PatternFly 6, Red Hat's open design system, used as it is: the family of
oVirt, Cockpit and the OpenShift console, which the people running qarax
already know. The UI uses PatternFly's framework-free CSS
(`@patternfly/patternfly`) with markup from the package's own `docs/`
examples: masthead and sidebar nav, page sections, cards and dashboards,
toolbars and tables, labels, inline alerts, empty states, modals, and its
status icons. Its tokens, Red Hat fonts and light and dark themes (following
the OS) come with it. qarax adds CSS only where PatternFly has no component.

- Status follows PatternFly's conventions (green ok, red error, blue in
  progress, grey for off, paused and unknown) and is never carried by colour
  alone: always an icon and a word.
- Anti-references: tables wider than the screen (keep to the columns that
  matter; the rest belongs on a detail page), custom look-alikes of
  PatternFly components, decoration PatternFly doesn't have.

Constraints: a SvelteKit single-page app in `webui/`, served by qarax-server
at `/ui`. Fonts are bundled, never loaded from a CDN (installs may be
air-gapped). Accessibility: WCAG 2.2 AA in both themes, as PatternFly
delivers it, visible keyboard focus, `prefers-reduced-motion` respected.

### Design Principles

1. **PatternFly first.** Reach for its component and its documented markup
   before writing CSS; a page should look like it belongs next to the
   OpenShift console.
2. **Explain, don't assume.** Every screen should make sense to someone who
   knows what a VM is but not what a PTY console is. Empty states and errors
   teach the next step.
3. **Calm by default, clear when it matters.** Neutral surfaces; colour is
   reserved for state, so a failure stands out without the page shouting.
4. **Same words everywhere.** Labels match the API and CLI vocabulary.
5. **Both themes are first-class.** Design and check every change in light and
   dark.
